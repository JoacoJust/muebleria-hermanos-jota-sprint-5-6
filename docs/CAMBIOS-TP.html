📋 Resumen General

Este documento explica en palabras sencillas los cambios realizados entre el TP anterior (Sprint 1-2) y el TP actual (Sprint 3-4). La transformación más importante fue pasar de un sitio estático a una aplicación cliente-servidor completa con backend propio.

1. Arquitectura: De Estático a Dinámico

❌ Antes (Sprint 1-2)

  • Sitio estático con HTML, CSS y JavaScript puro
  • Datos de productos "quemados" en el código JavaScript
  • Un solo archivo HTML con todo mezclado
  • Sin servidor backend
  • Sin separación de responsabilidades

✅ Ahora (Sprint 3-4)

  • Aplicación cliente-servidor con React + Node.js/Express
  • Backend propio con API REST para servir datos
  • Frontend React modular con componentes
  • Datos servidos dinámicamente desde el servidor
  • Separación clara: /backend y /client

2. Backend: Nuevo Servidor con Express

¿Qué es el backend?

El backend es el "cerebro" del servidor. Antes no existía; ahora creamos un servidor con Node.js y Express que se encarga de:

  • Recibir peticiones del frontend
  • Buscar los datos de productos
  • Devolver la información en formato JSON
  • Manejar errores (404, 400, 500)

Endpoints de la API (nuevas rutas)

Ruta Qué hace Estado
GET /api/productos Devuelve todos los productos JSON con array de productos
GET /api/productos/:id Devuelve un producto específico JSON con un producto o 404
GET /images/:archivo Sirve las imágenes de los productos Archivo de imagen

Middleware (nuevo concepto)

Los middleware son funciones que se ejecutan antes de llegar a las rutas. Implementamos:

  • Logger: Registra cada petición (método y URL) en la consola
  • express.json(): Convierte el cuerpo de las peticiones a JSON (para futuros POST)
  • CORS: Permite que el frontend (puerto 3000) hable con el backend (puerto 4000)
  • Helmet: Agrega headers de seguridad
  • Manejador de 404: Devuelve error JSON cuando no existe la ruta
  • Manejador de errores: Centraliza el manejo de errores

3. Frontend: Reconstrucción con React

¿Por qué React?

Reconstruimos todo el frontend desde cero usando React porque:

  • Permite crear componentes reutilizables
  • Maneja el estado de forma eficiente
  • Facilita la actualización de la UI cuando cambian los datos
  • Es el estándar moderno para desarrollo frontend

Componentes (nueva arquitectura)

Antes teníamos un JavaScript monolítico. Ahora tenemos componentes modulares:

Componente Responsabilidad
Navbar Barra de navegación con contador del carrito
Footer Pie de página con información de contacto
ProductCard Tarjeta individual de un producto
ProductList Lista de productos con filtros
ProductDetail Vista detallada de un producto
ContactForm Formulario de contacto controlado

4. Estado y Hooks (nuevo concepto)

¿Qué es el estado?

El estado es la "memoria" de la aplicación. Antes manipulábamos el DOM directamente. Ahora usamos hooks de React para manejar el estado de forma declarativa.

useState

Es el hook más básico. Sirve para guardar información que puede cambiar:

  • En ContactForm: Guarda los valores del formulario (nombre, email, mensaje)
  • En ProductList: Guarda los filtros (búsqueda, categoría, precio)
  • En App.js: Guarda el estado del carrito

Carrito de Compras

❌ Antes

  • Usaba Context API
  • Proveedor global en toda la app
  • Más complejo de entender

✅ Ahora

  • Estado en App.js
  • Pasado como props a través de Layout
  • Usa Outlet context de React Router
  • Más simple y explícito

5. Fetch y API (comunicación cliente-servidor)

¿Qué es fetch?

Fetch es la forma en que el frontend "pide" datos al backend. Antes los datos estaban en el mismo archivo JavaScript. Ahora:

  • El frontend hace una petición HTTP al backend
  • El backend responde con los datos en JSON
  • El frontend muestra los datos en la pantalla

Estados de la petición

Implementamos tres estados para la petición fetch:

  • Loading: Muestra un spinner mientras carga
  • Error: Muestra un mensaje de error si falla
  • Success: Muestra los datos cuando llegan

6. Formulario de Contacto

❌ Antes

  • Usaba react-hook-form (librería externa)
  • Usaba zod para validación (librería externa)
  • Más dependencias de las necesarias

✅ Ahora

  • Inputs controlados con useState puro
  • Validación manual en utils/validateContact.js
  • Sin dependencias externas para el formulario
  • Más simple y comprensible

7. Enrutamiento con React Router

¿Qué es React Router?

Antes no había navegación real. Ahora usamos React Router para:

  • Navegar entre páginas sin recargar
  • Tener URLs distintas para cada vista
  • Manejar rutas con parámetros (ej: /producto/:id)

Rutas implementadas

Ruta Vista
/ Home (página de inicio)
/productos Catálogo de productos
/producto/:id Detalle de producto
/carrito Carrito de compras
/contacto Formulario de contacto

8. Testing (nuevo)

¿Por qué tests?

Antes no había tests. Ahora implementamos pruebas automatizadas para asegurar que el código funciona correctamente:

Backend (Jest + Supertest)

  • Test de endpoint /api/productos
  • Test de endpoint /api/productos/:id
  • Test de validación de IDs inválidos
  • Test de 404 cuando no existe el producto
  • Test de JSON malformado

Frontend (React Testing Library)

  • Test de ProductList (estados loading, error, vacío)
  • Test de ContactForm (validación)
  • Test de Navbar (contador del carrito)
  • Test de ProductDetail (renderizado condicional)
  • Test de useCart (lógica del carrito)
  • Test de useProducts (fetch)

9. Calidad de Código (nuevo)

Herramientas de calidad

Implementamos herramientas para mantener el código limpio y consistente:

  • ESLint: Detecta errores y malas prácticas
  • Prettier: Formatea el código automáticamente
  • Husky: Git hooks que se ejecutan antes de commit
  • lint-staged: Lintea solo los archivos modificados
  • commitlint: Valida los mensajes de commit (Conventional Commits)

10. CI/CD con GitHub Actions (nuevo)

¿Qué es CI/CD?

Continuous Integration / Continuous Deployment. Antes no existía. Ahora:

  • Cada vez que se hace push, GitHub ejecuta los tests automáticamente
  • Si un test falla, se avisa inmediatamente
  • Garantiza que el código siempre funcione

11. Eliminación de Código Legacy

Carpeta legacy/

Eliminamos completamente la carpeta legacy/ que contenía el sitio estático de los Sprints 1-2. Esto significa:

  • No hay código viejo mezclado con el nuevo
  • El repositorio está limpio y organizado
  • Solo existe la versión actual con React + Express

13. Kit de Marca Oficial

Integración de marca

Antes usábamos SVGs de reemplazo. Ahora:

Conclusión

La transformación del Sprint 1-2 al Sprint 3-4 representa un salto cualitativo importante: pasamos de un sitio estático básico a una aplicación web moderna con arquitectura cliente-servidor, backend propio, frontend con React, testing automatizado, y herramientas de calidad de código. Este es el tipo de aplicación que se encuentra en el mundo real del desarrollo web profesional.
